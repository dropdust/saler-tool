# 销售获客工具（Saler Tool）宪法

## Core Principles

### I. 测试驱动开发（不可协商）

所有功能变更必须遵循"红 → 绿 → 重构"：先编写可复现目标行为的失败测试，再实现最小代码使其通过，最后重构。

- 新功能与缺陷修复必须先有失败测试，方可提交实现代码；禁止先实现后补测试。
- 测试分层必须齐备：领域逻辑用单元测试；Provider 适配器用假实现做契约测试（离线可跑）；关键链路用临时数据目录的集成测试。
- 禁止为了通过 CI 而删除、跳过或弱化测试；确需豁免时必须记录于计划的复杂度追踪并说明理由。

**Rationale**: 本产品包含抓取、批量发送等高风险副作用，测试是唯一可重复的回归安全网；TDD 同时保证 quickstart 验收场景始终可自动化复验。

### II. 面向对象与封装

领域逻辑必须以对象建模（实体、值对象、领域服务），依赖通过接口注入（依赖倒置），边界清晰。

- 核心领域层（`backend/src/saler/core/`）禁止直接依赖 FastAPI、桌面壳或任何外部服务 SDK；外部能力一律经 `providers/` 适配器接口接入。
- 禁止跨层直接访问数据库：数据访问必须经由仓储（repository）对象。
- 禁止共享可变全局状态；并发与后台协作必须经由明确的对象与队列。
- 前端以组件为边界：视图与组件只依赖本地 API 契约，不内嵌业务规则。

**Rationale**: 桌面壳、数据库与外部服务商都将演进（pywebview→Tauri、SQLite→PostgreSQL、Provider 增删），只有严格的对象边界才能让这些替换成为局部改动。

### III. 约定大于配置

遵循既定约定组织代码与数据；新增内容按约定放置即可被发现，用户零配置即可用。

- 目录结构、命名、接口路径与文件格式必须遵循 `plan.md` 项目结构与 `contracts/` 契约；契约变更必须同步更新契约文件。
- 扩展点必须零配置发现：新增 Provider 只需实现接口并注册 manifest，不需要修改前端或其他模块。
- 默认值必须开箱即用；只有确实需要用户决策的项才暴露为配置，且必须提供合理默认。

**Rationale**: 单用户桌面工具最稀缺的资源是使用者的注意力与维护者的时间；约定把"决策成本"变为"查文档成本"。

### IV. 技术栈限定

主技术栈固定为：后端 **Python（≥ 3.12）**，前端 **TypeScript（5.x）+ Vue 3**，以桌面应用形态覆盖 Windows / macOS / Linux。

- 未经宪法修订，禁止引入其他主流语言或前端框架作为实现主体。
- 新增第三方依赖必须评估安全性、体积与维护活跃度；桌面端拒绝重量级捆绑（如随包捎带整套服务端网关）。
- 技术细节演进（如桌面壳选型、数据库版本）在 plan 与 research 中决策，不构成本原则的修改。

**Rationale**: 技术栈是用户明确的选型；书面限定防止栈漂移与依赖膨胀，让长期维护成本可预期。

### V. 密钥零入库

任何密钥与凭证（大模型密钥、邮箱授权码、短信/检索服务凭据）一律禁止写入代码。

- 禁止出现于：源码、常量、默认配置、示例文件、测试夹具、日志、报错信息、导出物与 git 提交历史。
- 凭证只由用户在运行时提供，必须加密存储（OS 钥匙串 + 字段级加密）；界面、日志与导出一律脱敏。
- 测试必须使用假 Provider 与占位值；一旦发现真实密钥入库，必须立即吊销该密钥并清理历史。

**Rationale**: 数据主权产品以信任为生命线；桌面分发意味着一旦泄露无法撤回，代价不可接受。

## 附加约束（平台、数据与依赖）

- 交付形态：三平台桌面应用功能一致；离线状态下必须可查看与管理本地数据。
- 数据主权：业务数据默认保存在用户本机；任何对外调用（大模型、检索、发送）必须由用户主动触发且对其可见可控。
- 合规支持：退订/黑名单、发送限频、礼貌抓取为必备能力；合规的最终责任在用户，产品必须提供工具与提示，不替代用户判断。
- 界面语言：中文优先；营销内容支持多语言。
- 演进兼容：领域层与 API 面的设计不得阻碍未来"企业 Web 服务统一维护数据资产"的版本路线。

## 开发工作流与质量门

- 规格驱动：新功能必须经由 Spec Kit 流程（`/speckit-specify` → `/speckit-plan` → `/speckit-tasks` → `/speckit-implement`）；`tasks.md` 勾选状态是进度的唯一事实。
- **逐任务提交（用户要求，2026-10-10）**：每完成 `tasks.md` 中的一个任务，必须立即执行一次 git 提交（任务与其测试在同一提交内，方便项目管理与回溯）；提交信息必须包含任务 ID 并说明"为什么"（例如 `T030: 图谱服务——FR-007~011`）。禁止将多个任务攒成一次大提交；确因原子性需要跨任务合并时，必须在提交信息中写明理由。
- 质量门：合并前必须满足——测试全绿、契约同步、`checklists/requirements.md` 无未决项；发布前必须通过每平台"冻结包冒烟"（quickstart S1/S6/S10）。
- 一致性审查：关键变更后运行 `/speckit-analyze`；工件间冲突以 `spec.md` 为准。
- 自我评审：即便单人开发，也须以 diff 审查加测试证据的方式自我评审；提交信息必须说明"为什么"。
- 文档同步：技术决策记录于 `research.md`；接口变化必须同步 `contracts/`。

## Governance

- 修订程序：任何修订必须（1）书面提出条款变更与理由；（2）评估对规格、计划与任务的影响；（3）按语义化版本递增版本号；（4）在文件头部生成 Sync Impact Report；（5）经项目所有者批准后生效。
- 版本策略：MAJOR——不兼容的治理/原则移除或重定义；MINOR——新增原则或实质扩展条款；PATCH——措辞澄清与非语义修订。
- 合规审查：所有提交与评审必须验证本宪法；违反必须记录于计划的复杂度追踪并说明豁免理由，未记录即视为阻塞项。
- 效力：本宪法优先于其他实践约定；与之冲突的文档必须按修订程序更新。
